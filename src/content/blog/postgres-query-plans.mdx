I have been writing SQL for five years. I have added indexes when things felt slow. I have not, until last week, read a single `EXPLAIN ANALYZE` output and understood what it was telling me. That is now embarrassing in the way that the things you should have learned earlier always are.

The query was a join between a `patients` table and an `events` table, filtered by patient id and a date range, ordered by date. It ran in four seconds against a copy of production data. I assumed I needed an index on `patient_id`. I added one. The query stayed at four seconds.

Then I read the plan.

## The fix that worked

The single index I needed was `(patient_id, occurred_at DESC)`. Composite, ordered, covering both the filter and the sort. Query dropped to forty milliseconds.

## The lesson I should have learned earlier

Indexes are not "speed up the column you filter on." Indexes are data structures the planner picks from. If the planner cannot use the index in the shape your query needs, the index does not exist for that query. `EXPLAIN ANALYZE` is the only way to know which one you actually wrote.
